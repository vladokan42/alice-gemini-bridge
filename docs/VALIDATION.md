# Проверки и известные ограничения

## Статус

**Эксперимент: физическая голосовая приёмка ожидается.** На предыдущем
варианте гибрида был живой цикл микрофон → Gemini через OmniRoute → родной
голос Алисы. Затем обнаружилась ошибка распознавания до вызова LLM.
Последние исправления обработки микрофонных служебных сообщений,
непрерывного приёма и управляющих событий требуют повторной проверки.

**После этих изменений полный голосовой цикл на физической колонке не
подтверждён. Установка «пустой сервер + подготовленная колонка» с нуля на
реальном оборудовании также не подтверждена.** Успех сборки, синтетических
тестов, HTTP health, `check` или `-query` не закрывает эти пункты.
Широкая совместимость с моделями колонок/firmware не заявляется.

Новая схема проверена на отдельном свежем **оригинальном OmniRoute 3.8.52**:
выбор релиза и проверка версии образа, запуск по digest только на loopback,
вход администратора, создание тестовых подключения/комбо/ограниченного ключа
через API оригинала и обратное чтение разрешений. Сам `server` больше не
копирует эту логику настройки — пользователь выполняет её в UI OmniRoute.
`configure` успешно сохранил подключение после генерации и отказов HTTP
`401/403` для анонимного запроса, управления и тестовой прямой модели.

Получен **настоящий ответ Gemini** по цепочке «свежий оригинальный OmniRoute →
собственный существующий разрешённый шлюз с CLI-доступом → Gemini». Это не
проверка нового OAuth-входа в Google и не голосовая приёмка. Возврат остановил
только тестовый stack по сохранённому digest, не обращаясь к latest, и сохранил
его том. После проверки тестовые контейнеры, сеть, том и закрытые временные
файлы удалены; существующие контейнеры не изменились.

Ранее, до отделения сервисов, на OmniRoute 3.8.51 отдельно проверялось
восстановление данных остановленного тома вместе с исходными encryption secrets
в новый изолированный экземпляр: вход, комбо, права и ответ через собственный
шлюз проходили. Это историческая проверка другой версии, не доказательство
восстановления свежего CLI / OAuth-подключения или физической колонки.

В коде есть предварительные проверки, закрытые резервные копии, запрет
перезаписи состояния и защитный возврат. Само наличие этих проверок не
означает, что все аппаратные отказы и восстановление уже испытаны.

## Воспроизводимые проверки без колонки и реального ключа

Нужны Git, Make, Python 3, Go с поддержкой загрузки toolchain и C-компилятор
для race-тестов. Версию Go задаёт `go.mod` **скачанного оригинального Quasar**,
а не этот репозиторий. На поддерживаемом сервере: `sudo apt-get install -y make gcc libc6-dev`.
Go может скачивать toolchain и зависимости; «без ключа» не означает «без сети».
Из **чистого checkout** этого репозитория:

```sh
make test
make build
./bin/quasar-bridge -config config.example.json -check-config
./bin/quasar-bridge -config config.example.json -route 'Поставь будильник на семь утра'
./bin/quasar-bridge -config config.example.json -route 'Почему небо голубое'
sh ./install.sh --dry-run
```

Ожидаемые маршруты — `yandex` и `llm`. Эти команды не устанавливают ничего на
колонку и не вызывают настоящий LLM. Маршруты сверяются с
[`examples/route-cases.json`](../examples/route-cases.json).

- **`make test`** — наши Python-тесты `packaging/` и `scripts/` и shell syntax,
  без скачивания сервисов. Проверяются маршруты установки/возврата,
  выбор стабильного релиза, проверка образа, конфликт патча и отказ при старом
  результате проверок после изменения исходника.
- **`make build`** — скачивает последний stable оригинального Quasar в новый
  игнорируемый каталог `.upstream/quasar-bridge`, проверяет патч, затем выполняет
  `go test -race -count=1 ./...`, `go vet ./...`, сборку, проверку конфига и
  маршрутов. Только после успеха появляется проверяемая сборка `bin/quasar-bridge`.
  Версии и SHA-256 записываются в `.upstream/quasar-bridge/integration-receipt.json`.

Повторный `make build` **откажет при существующем каталоге исходника**: сначала
проверь и сохрани прежний комплект или используй новый checkout. Чтобы повторно
собрать уже проверенный неизменный исходник без поиска latest:

```sh
python3 scripts/upstream.py build
```

Для отдельной проверки другого стабильного релиза выбери новый каталог и
настоящий тег автора, например через `scripts/upstream.py bridge --directory ... --version ...`.
Это не способ обойти тесты. Изменённые исходник или патч запрещают сборку по
старой квитанции проверки. Отпечаток охватывает весь скачанный модуль,
а не только текущие папки Go-пакетов. Внешний Go workspace отключён; локальные
`replace` зависимостей не поддерживаются и останавливают сборку. Квитанция
с неуспешными тестами, неполными полями или чужим commit также не принимается.
Не добавляй файлы в проверенный исходник между проверкой и повторной сборкой.

Тесты охватывают native cue, речевой протокол, маршрутизацию, синтетические
boot/возврат, ограничения установщика и сканер публикуемого дерева.
Подменённые SSH, firmware, mount/reboot и API — **тестовые модели, не живые устройства**.
Число тестов намеренно не закреплено в документации; смотри результат
проверки конкретного commit.

При необходимости отдельно собери переносимый ARM64-комплект:

```sh
make bundle
```

`make bundle` только создаёт новый `dist/`, не ставит hook и не запускает
бинарник на колонке. Если `dist/` уже есть, команда откажет: сначала проверь
и сохрани прежний комплект, не удаляй его вслепую.

Проверка публикуемых файлов:

```sh
python3 scripts/check-public-tree.py
```

Сканер читает **Git index**, а не все непроиндексированные файлы. Его успех
не доказывает чистоту текущего рабочего дерева или Git history. Перед
публикацией отдельно просмотри фактический diff, состав index и историю.
CI проверяет committed дерево, не непереданные локальные изменения.

## Проверка своего OmniRoute

На сервере после установки:

```sh
sudo python3 scripts/install.py check
```

С `--state-dir` укажи тот же каталог, который использовался при установке.
Команда читает закрытый `station.json` и проверяет:

- содержательный ответ `POST /v1/chat/completions` с ограниченным ключом и
  именем своего комбо из `station.json`;
- HTTP `401/403` для анонимного запроса генерации;
- HTTP `401/403` для `/api/keys` с ключом колонки, без admin cookie.

Этап `configure` дополнительно требует `401/403` при тестовом прямом запросе
`gemini/blocked-direct-probe` с ключом колонки. Обычный `check` **не повторяет**
эту пробу. Один запрещённый запрос не доказывает запрет всех остальных моделей:
владелец обязан отдельно сверить в UI права `inference`, ограничение только
своим комбо и отсутствие прямых моделей и управления.

Успешный `check` расходует лимиты подключения и доказывает доступ **с сервера**, не
с колонки. Установщик до установки hook выполняет на самой колонке
`-check-config` и `-check-backends`. Для повторной проверки уже установленного
комплекта из корня репозитория на сервере:

```sh
sudo ssh alice-speaker 'sh /data/opt/quasar-bridge/start.sh -check-config'
sudo ssh alice-speaker 'sh /data/opt/quasar-bridge/start.sh -check-backends'
```

Последняя команда обращается к LLM, но не включает микрофон и не проверяет
озвучивание. Не публикуй `runtime.env`, `gateway.env`, `station.json`, ключи,
сырые HTTP-ответы, admin cookie и токены для подтверждения успеха.

## Что нужно для физической приёмки

Следуй [инструкции установки](INSTALL.md), сохрани физический доступ и
независимую SSH-сессию. Установщик сам не перезагружает колонку. На первом
запуске hook действует 10-минутный таймер возврата; **не подтверждай заранее**.

1. **Новый boot и автозапуск.** Свой единственный hook, один мост, listener
   только `127.0.0.1:18861`, ровно свой read-only bind и HTTP health. Работа без
   ADB/reverse/временного туннеля с ноутбука.
2. **Полный вопрос.** `VoiceInput` → переданные mic controls → final ASR →
   OmniRoute → Gemini HTTP 200 → `nativeTtsGenerate`/finish → **один слышимый
   содержательный ответ**. Одного HTTP 200 недостаточно.
3. **«Думаю».** Короткая фраза слышна до ответа, не повторяется текстом LLM и
   не перекрывает основную речь.
4. **Следующий вопрос.** Уточнение использует контекст; несколько новых
   вопросов подряд доходят до ASR/LLM и получают ответ. Управляющие события
   продолжают проходить, приём не прекращается после первого ответа.
5. **Отмена.** «Стоп» прекращает речь; поздний ответ отменённого запроса не
   воспроизводится, новый вопрос после остановки работает.
6. **Штатный маршрут.** Безопасная команда выполняется Яндексом. Нужные
   будильники, музыку и устройства проверяй отдельно: одного решения `yandex`
   недостаточно, чтобы заявить работу всех функций.
7. **Подтверждение оператором.** Только после успеха голосовых пунктов запусти
   `sudo python3 scripts/install.py confirm --ssh alice-speaker` и введи `YES`.
   `confirm --yes` запрещён. Скрипт сверяет новый boot, свой hook/mount,
   конфиг и health, но слышимость подтверждает человек.
8. **Повторный boot.** Контролируемая перезагрузка после подтверждения и
   повторение голоса/остановки/штатной команды.
9. **Возврат.** `rollback --target speaker --ssh alice-speaker` → точный
   stock-конфиг → контролируемая перезагрузка → штатная Алиса без моста.
   Успешное сравнение файла до reboot не устраняет кеш endpoint в процессе.

Отдельно, в безопасное окно с физическим доступом, остаётся испытать отсутствие
`confirm` до истечения таймера, недоступность LLM, повторные падения и отказ
на чужом mount. Автоматика должна возвращать только собственное состояние,
не ломать доступ и не уходить в бесконечную перезагрузку. При отказе проверки
нужен локальный способ восстановления, не принудительный `umount`.
Испытание этих отказов — отдельная проверка, не обязательный эксперимент
на рабочей колонке во время первой голосовой пробы.

Также отдельно проверь восстановление закрытой резервной копии на пустом
сервере: данные тома **вместе с** `gateway.env`, `station.json` и метаданными,
затем вход администратора, границы ключа, доступ с колонки и голос.
Порядок копирования приведён в [INSTALL.md](INSTALL.md#9-закрытая-резервная-копия-и-восстановление-сервера).
Переезд в офис/VPN требует повторения сетевой и голосовой проверки:
VPN на ноутбуке не подтверждает маршрут от колонки.

## Диагностика голосовой ошибки

- **`check` или `-check-backends` не проходит:** проверь частный маршрут,
  `/v1`, комбо, точный model ID в OmniRoute, регион сервера, состояние своего
  CLI / OAuth-подключения, его лимиты и TLS. Не отключай TLS и не открывай публичный порт.
- **Сервер проходит, колонка — нет:** проверь доступ именно колонка → сервер,
  firewall и сеть/VPN устройства. Его loopback — не loopback сервера.
- **Есть `VoiceInput`/ack, но нет final ASR**, затем `waitForResult timeout`:
  сбой до Gemini. Смотри mic `SpotterEnd`/`Close` и
  `native_mic_control` с `forwarded`, не меняй модель наугад.
  `StreamControl.MessageId` может отличаться от `VoiceInput.MessageId`:
  неизвестный служебный ID не должен считаться заведомо устаревшим запросом.
- **Final ASR есть, LLM-ответа нет:** проверь статус/таймаут OmniRoute и Google.
  Не публикуй текст вопроса и заголовок Authorization.
- **LLM 200 есть, звука нет:** проверь native TTS, finish и реальную слышимость.
  Интерфейс OmniRoute и локальный health не подтверждают динамик.
- **После возврата голос идёт не туда:** сверь оригинал и принадлежность mount.
  Работающий голосовой процесс может кешировать endpoint; после успешного
  возврата нужен контролируемый reboot. Не переписывай stock-файл поверх mount.
- **Истекли 10 минут:** не обходи `disabled` ради продолжения. Проверь,
  вернулась ли штатная Алиса; `acceptance.failed` означает незавершённую
  приёмку, а не разрешение автоматически переустановить поверх состояния.

Связывай события конкретного прогона с request ID локально. В публичный Issue
передавай commit, модель/firmware, этап и очищенную последовательность событий,
не полный лог, адреса своей сети, идентификаторы аккаунта, конфиги или аудио.
