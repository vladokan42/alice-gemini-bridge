# Установка: прошитая колонка и пустой сервер

> **Эксперимент, не готовый надёжный продукт.** Физическая установка всего
> контура с нуля и голосовой цикл после последних исправлений ещё не приняты.
> Автотесты и успешный API-запрос этого не доказывают. Прочитай
> [статус проверок](VALIDATION.md) и [правила безопасности](../SECURITY.md).

Основной путь: колонка → OmniRoute → Gemini через подключённый CLI / OAuth.
Мастер скачивает сервисы из оригинальных проектов и ставит интеграцию на уже
подготовленную колонку. Он **не**
прошивает устройство, не получает root и не настраивает доступ к аккаунту Яндекса.
Все команды ниже выполняются **на сервере из корня репозитория**, если не указано иное.
Адреса `*.example.invalid` — заглушки: замени их своими частными адресами локально.

## 1. Что подготовить

- Сервер с Debian 13 или Ubuntu 24.04, `sudo`, свободным частным IPv4 и портом
  `20128`. Адрес должен быть назначен самому серверу и доступен с колонки.
  Для нового контура нужен поддерживаемый Docker образ; иные ОС/архитектуры
  не считаются проверенными только по наличию Docker.
- Доступ сервера к пакетам ОС, GitHub, Go toolchain/модулям, реестру Docker и
  endpoint выбранного CLI / OAuth-провайдера. Docker и Compose мастер поставит при отсутствии;
  работающий Docker не перезапускает, существующие проекты не заменяет.
- Своя колонка с root, рабочим SSH по ключу и заранее известным достоверным
  отпечатком ключа хоста. Парольный вход мастер не использует.
- Физический доступ, отдельная SSH-сессия для возврата и проверенный способ
  восстановления своей firmware. Таймер не заменяет этот доступ.
- Доступ к Gemini через CLI в OmniRoute: владелец сам подключает Google-аккаунт
  через поддерживаемый шлюзом CLI / OAuth-провайдер. Ключ Google AI Studio не
  требуется. Условия провайдера, лимиты аккаунта и доступность моделей сохраняются.
  Этот комплект не предоставляет аккаунты, подписки или обход ограничений.
- Новый пароль администратора OmniRoute: одна строка, **не меньше 16 знаков**,
  без обратного слеша (`\`).
  Сохрани его в своём менеджере паролей.

Колонке нужны Linux ARM64 (`uname -m` → `aarch64`), автозапуск SysV init, конфигурация
`/system/vendor/quasar/quasar.cfg`, исполняемый `/etc/init.d/S99quasar`, штатный
CA bundle `/system/vendor/quasar/ca-certificates.crt`, `/proc/self/mountinfo`,
boot ID и наложение файла без права записи (read-only file bind). Нужны команды BusyBox,
включая `tar`, `wget`, `start-stop-daemon`, `sha256sum`, `mount`, `umount`,
`logger`, `mktemp`, `ln`, `sync` и `reboot`.

Ранее исходный гибрид испытывался на `yandexmicro`, firmware `0.369.1.46`.
Это не матрица совместимости и не приёмка текущей версии. Root не доказывает
совместимость речевого протокола. Если пути/init/архитектура отличаются,
**остановись**, а не подгоняй firmware командами из инструкции.

## 2. Скачать и прочитать исходник

Если Git и SSH-клиент ещё не установлены:

```sh
sudo apt-get update
sudo apt-get install -y git ca-certificates openssh-client
```

```sh
git clone https://github.com/vladokan42/alice-gemini-bridge.git
cd alice-gemini-bridge
git rev-parse HEAD
```

Сохрани commit для своей проверки. Прочитай локальные `install.sh`,
`scripts/install.py`, `scripts/upstream.py`, `patches/quasar-integration.patch`
и `packaging/install-device.sh` до запуска с правами root.
Не используй `curl ... | sudo sh`. Секреты не должны попадать в checkout.

В этом репозитории нет исходного дерева или бинарников Quasar Bridge и OmniRoute.
Оригиналы загружаются с GitHub:
[Quasar Bridge](https://github.com/skrashevich/quasar-bridge) и
[OmniRoute](https://github.com/cheaper-inference/OmniRoute). История Git содержит
прежнюю адаптацию, но установщик её не использует и не возвращается к ней при сбое.

## 3. Подготовить SSH именно для root на сервере

`sudo sh ./install.sh` запускает SSH от root. Проверенный вход обычного
пользователя не означает, что мастер увидит его ключ, config и known_hosts.

```sh
sudo install -d -m 0700 /root/.ssh
```

Закрытым способом перенеси на сервер **свой уже разрешённый на колонке ключ**,
размести его в `/root/.ssh/alice-speaker`: владелец root, права `0600`.
Не вставляй ключ в shell-команду, чат или Git. Не заменяй существующий файл.
Если ключ защищён паролем, заранее обеспечь разрешённый неинтерактивный доступ
для этой root-сессии; мастер не спрашивает пароль ключа и не обходит защиту.

Добавь через локальный редактор в `/root/.ssh/config`, сохранив другие записи.
Если есть общие правила `Host *`, размести этот блок перед ними:

```sshconfig
Host alice-speaker
    HostName speaker.example.invalid
    User root
    Port 22
    IdentityFile /root/.ssh/alice-speaker
    IdentitiesOnly yes
    UserKnownHostsFile /root/.ssh/known_hosts.alice-speaker
    StrictHostKeyChecking yes
    BatchMode yes
```

Замени `HostName` и при необходимости порт. Перед первым входом получи
кандидат ключа хоста; при другом порте добавь тот же `-p` к `ssh-keyscan`:

```sh
sudo sh -eu -c 'umask 077; set -C; ssh-keyscan -T 5 speaker.example.invalid > /root/.ssh/alice-speaker.hostkey.candidate'
sudo ssh-keygen -lf /root/.ssh/alice-speaker.hostkey.candidate
```

**Сравни отпечаток с заранее проверенным через доверенный канал.** Сам
`ssh-keyscan` не подтверждает личность устройства. При несовпадении остановись.
Только после совпадения сохрани проверенный ключ без перезаписи старого:

```sh
sudo sh -eu -c 'umask 077; set -C; cat /root/.ssh/alice-speaker.hostkey.candidate > /root/.ssh/known_hosts.alice-speaker'
sudo chmod 0600 /root/.ssh/config /root/.ssh/alice-speaker /root/.ssh/known_hosts.alice-speaker
sudo ssh alice-speaker 'id -u; uname -m; readlink -f /system/vendor/quasar/quasar.cfg; test -x /etc/init.d/S99quasar; test -r /system/vendor/quasar/ca-certificates.crt'
```

Ожидаются root (`0`), `aarch64` и подходящий реальный путь конфига. Проверь
каждый результат; команда не должна запрашивать пароль или принимать новый
ключ хоста. Не отключай `StrictHostKeyChecking` ради продолжения.

## 4. Запустить мастер всего контура

```sh
sh ./install.sh --dry-run
sudo sh ./install.sh --ssh alice-speaker
```

`--dry-run` у `install.sh` только описывает действия: ничего не ставит,
не проверяет пакеты/колонку и не доказывает совместимость.
Обычный запуск ставит недостающие пакеты ОС: Python 3, Git, OpenSSH-клиент,
Go, C-компилятор для race-тестов, Docker Engine и Compose. При необходимости запускает Docker, но не
перезапускает уже работающую службу и не меняет правила firewall вручную.
Затем запускает `python3 scripts/install.py all`: `server`, пауза для CLI / OAuth,
`configure`, затем `speaker`. На колонку Go и Python не ставятся. Версия
компилятора выбирается по `go.mod` скачанного оригинала; для загрузки toolchain нужен доступ в сеть и
разрешённый `GOTOOLCHAIN=auto`.

Ответь на вопросы мастера:

1. **Конкретный частный IPv4 сервера**, доступный с колонки. Не `0.0.0.0`,
   публичный IP или имя хоста. Loopback допустим для локальной проверки,
   но колонка не сможет обратиться к loopback другого компьютера.
2. **Новый пароль администратора** от 16 знаков — ввод скрыт; затем `INSTALL`
   для подтверждения создания отдельного сервера.
3. В открывшемся интерфейсе оригинального OmniRoute подключи свой **CLI / OAuth**,
   создай комбо для Gemini и отдельный ключ: только `inference`, только это комбо,
   без прямых моделей и управления, с `noLog`. Веб-вход выполняешь сам.
4. Вернись в терминал, введи `READY`, адрес `/v1`, точное имя своего комбо
   (например, `omni-alice-lite` или `alice-gemini`) и ограниченный ключ OmniRoute.
   Ключ вводится скрыто, не ключ Google и не OAuth-токен.
5. Мастер проверит генерацию и запреты доступа; затем запросит подтверждение
   `INSTALL` для скачивания, проверки и установки моста на колонку.

Если прервал работу после создания сервера, он остаётся запущен отдельно.
Закончи настройку в его UI, затем используй `configure` и `speaker`, не повторяй `all`.

Безопаснее идти интерактивно: `--yes` не нужен. Можно изменить порт через
`--port`, каталог через `--state-dir`; тогда используй их последовательно
в `server`, `speaker`, `check` и серверном возврате. По умолчанию:

| Где | Что создаётся |
| --- | --- |
| Сервер `/opt/alice-gemini`, каталог `0700` | `compose.json`, `stack.json` с исходным релизом и digest, `gateway.env`; после `configure` — `station.json`, после `speaker` — закрытая копия `speaker-backup/original.cfg`; файлы `0600` |
| Docker | Отдельный Compose-проект со случайным именем `alice-gemini-…`, свой именованный том данных |
| Колонка `/data/opt/quasar-bridge`, каталог `0700` | Статический ARM64-бинарник из оригинального исходника с патчем, `upstream.json` с commit и SHA-256 патча/исходника, лицензии, конфиг, закрытый `runtime.env`, `original.cfg`, `candidate.cfg`, скрипты возврата |
| Колонка `/etc/init.d/S98quasarbridge` | Единственный новый скрипт автозапуска (hook) перед штатным `S99quasar` |

### Что происходит на сервере

Мастер один раз запрашивает **последний стабильный релиз оригинального OmniRoute**,
скачивает соответствующий `diegosouzapw/omniroute:<версия>`, проверяет версию
внутри образа без сети и сохраняет `image@sha256:…` в `compose.json`/`stack.json`.
Если GitHub, образ или его версия не сходятся, установка останавливается:
встроенной старой версии нет. `latest` не остаётся плавающим тегом в Compose.

Создаются случайные JWT/API/encryption secrets, обязательный API-ключ и вход
администратора. **Подключения, комбо и ключ колонки настраивает владелец в UI
оригинального проекта**, а не скрипт с копией старой логики OmniRoute.
После этого `configure` проверяет реальный ответ, отказ анонимному запросу,
отказ в управлении и запрет тестового прямого запроса к модели.
Это проверка поведения, не полный аудит всех прав: сверь ограничения своего ключа в UI.

Сессия CLI / OAuth хранится только в данных OmniRoute; пароль и секреты шлюза —
в `gateway.env`. `station.json` содержит ограниченный ключ колонки, URL и имя
комбо. Не печатай эти файлы. Чужие OAuth-сессии и настройки существующего шлюза
не импортируются и не меняются.

Порт `20128` привязывается к `127.0.0.1` и выбранному частному IP сервера.
Адрес колонки будет `http://<частный-IP-сервера>:20128/v1`, модель —
имя твоего комбо. Это HTTP: используй только доверенную изолированную LAN
или защищённый VPN-маршрут. Мастер не добавляет TLS, DNS, публичный туннель
и обход firewall. Доступность из LAN сама по себе не означает безопасность
общей гостевой/офисной сети. Управляющий UI доступен на том же порту:
ограничения доступа к серверу — ответственность владельца.

### Что происходит на колонке

До изменений мастер проверяет архитектуру, пути, SSH и отсутствие своего
старого каталога, любого существующего hook и чужого file mount на конфиге.
После read-only проверок скачивает последний стабильный **оригинальный Quasar
Bridge**, фиксирует commit и проверяет применение `patches/quasar-integration.patch`.
Затем запускает исходные и добавленные Go race-тесты, `go vet`, проверку нашего
конфига и всех примеров маршрутов. Патч добавляет «Думаю», persona и исправления
микрофона/отмены; это модифицированная сборка, не нетронутый бинарник автора.
Конфликт патча или неуспех тестов останавливает работу **до записи на колонку**.
Обхода проверки и возврата к копии старого исходника нет.

Из проверенного исходника собирается статический ARM64-бинарник, сохраняется
закрытый оригинал и формируется копия firmware-конфига. **Только в копии** меняются:

- `aliced.uniProxyUrl` → `ws://127.0.0.1:18861/uni.ws`;
- `aliced.uniProxyQuicUrl` → пустая строка.

Переданный комплект считывается обратно и сравнивается по SHA-256 без
публикации хешей ключа и firmware-конфигов. На самой колонке выполняются
`-check-config` и `-check-backends` **до установки hook**. Затем новый hook
устанавливается атомарно с отказом при занятом имени; исходный режим корневой
файловой системы (rootfs) восстанавливается. Штатные `quasar.cfg`, `launch.json`
и `S99quasar` не переписываются.
Read-only bind применяется при запуске hook после готовности локального моста.

## 5. Проверить сервер, перезагрузить и принять голосом

После успеха мастера сначала:

```sh
sudo python3 scripts/install.py check
```

Команда проверяет ответ выбранного комбо, отказ анонимному запросу и отказ
ограниченному ключу в управлении. `configure` дополнительно проверяет отказ
тестовому прямому обращению к модели. Успешный `check` расходует лимиты подключения;
он **не проверяет микрофон, динамик, SSH или запуск после reboot**.

**Автоматической перезагрузки в `all` нет.** Открой независимую SSH-сессию для
возврата, убедись в физическом доступе и выполни напечатанную мастером команду:

```sh
sudo ssh alice-speaker reboot
```

Первый запуск нового hook с `acceptance.pending` запускает независимый от SSH
и основного процесса таймер **на 10 минут**. За это время после загрузки проверь:

1. Новый вопрос → «Думаю» → один слышимый содержательный ответ.
2. Короткое уточнение с контекстом.
3. «Стоп» прекращает речь; поздний ответ не начинает говорить снова.
4. Безопасную штатную команду, например запрос времени; затем нужные тебе
   бытовые действия отдельно. Маршрут `yandex` не доказывает реальное действие.

Только после успеха:

```sh
sudo python3 scripts/install.py confirm --ssh alice-speaker
```

Введи `YES`. `confirm --yes` **запрещён**: это личное подтверждение проверки
голоса. Скрипт дополнительно требует новый boot, свой hook, ровно свой
записанный mount, конфиг-кандидат и HTTP health. Эти технические условия сами
по себе не доказывают слышимый ответ.

Без подтверждения таймер ставит `disabled`, снимает **только свой** записанный
bind, сверяет оригинал и перезагружает колонку на штатный маршрут. При чужом
или неоднозначном mount возврат отказывается и требует локального
восстановления; принудительного `umount` нет. Это не защита от всех зависаний
и не голосовая пасхалка. Отдельный supervisor после повторных быстрых падений
тоже отключает мост и пытается безопасно вернуть штатный маршрут.

После подтверждения сделай ещё один контролируемый reboot и повтори голосовую
проверку без ADB/reverse/туннелей. Полные критерии — в
[VALIDATION.md](VALIDATION.md#что-нужно-для-физической-приёмки).

## 6. Раздельная установка и существующий OmniRoute

Если зависимости уже стоят, можно выполнить те же этапы отдельно:

```sh
sudo python3 scripts/install.py server
# Подключи свой CLI / OAuth, создай комбо и ограниченный ключ в UI.
sudo python3 scripts/install.py configure
sudo python3 scripts/install.py speaker --ssh alice-speaker --dry-run
sudo python3 scripts/install.py speaker --ssh alice-speaker
sudo python3 scripts/install.py check
```

`speaker --dry-run` требует готовый `station.json`, загружает его локально и
по SSH выполняет только предварительные проверки; не создаёт файлов,
mount/hook и не перезагружает устройство. Успех не проверяет будущую речь.

Для **уже работающего OmniRoute** не запускай `all/server`: они создают новый
экземпляр. Самостоятельно настрой доступный с колонки `/v1`, своё комбо
и отдельный ключ с указанными выше ограничениями. Проверь запрет анонимного
запроса, управления и прямых моделей. Затем выполни:

```sh
sudo python3 scripts/install.py configure \
  --base-url https://omniroute.example.invalid/v1 \
  --model omni-alice-lite
```

Вместо примера укажи свой URL и точное комбо. Для доверенной LAN допустим
`http://<частный-IP-сервера>:20128/v1`. Мастер скрыто спросит ключ, выполнит
проверки и создаст каталог root/`0700` и `station.json` root/`0600`.
Если каталог уже создан командой `server`, проверит принадлежность stack и
добавит только отсутствующий `station.json`. Чужой каталог и повторную настройку
поверх готового `station.json` не принимает. Затем запусти `check`,
`speaker --dry-run` и `speaker`, после установки — reboot/голос/`confirm`
по разделу выше. В этом режиме мастер не управляет провайдером, OAuth,
томами или паролем существующего OmniRoute; серверный `rollback` неприменим.
Прямой Google OpenAI-совместимый endpoint возможен как отдельная ручная
настройка моста, но не подставляется в этот `station.json`: мастер ожидает
OmniRoute с его проверками прав.

## 7. Ошибка и повторная попытка без перезаписи

**Новые установки не закреплены за старой версией сервисов.** По умолчанию
используется `latest` stable оригинального проекта на момент скачивания.
Чтобы осознанно повторить известный релиз, передай точные стабильные теги
`--bridge-version vX.Y.Z` и `--omniroute-version vA.B.C` соответствующему этапу.
Это примеры формата, а не действующие теги. Только оригинальные репозитории,
никаких веток, произвольных URL, preview-релизов или отключения проверок.

Уже установленный контур **не обновляется автоматически**. Не меняй digest в
рабочем `compose.json` на `latest`: сначала закрытая копия и проверка восстановления,
проверка новой интеграционной сборки отдельно, затем согласованная замена с
физическим доступом и готовым возвратом. Если патч перестал подходить, его надо
адаптировать и проверить в этом проекте; не подставлять старое полное дерево.
Сохранённые `stack.json`, `upstream.json`, бинарник и данные относятся к конкретной
установке. Возврат не ищет текущий latest и не требует новую версию для восстановления.

- Неправильная ОС, ключ хоста, пароль, IP, занятый порт, недоступная модель,
  TLS, доступность шлюза или отсутствие команды — причина остановки, не обхода проверки.
- Существующие `/opt/alice-gemini`, `speaker-backup`, каталог колонки, hook
  или чужой mount нельзя удалять только ради повторного запуска мастера.
  Автоматического продолжения/обновления поверх них нет.
- Если сервер готов, а этап колонки ещё **не создал** свой каталог/резерв,
  исправь причину и запускай только `speaker`, не `all`.
- При сбое серверного этапа мастер пытается остановить только свой stack;
  каталог и том остаются. Если остановка не удалась — используй серверный
  `rollback` ниже. Сначала сохрани состояние и выясни, какие шаги выполнены.
- После частичной установки на колонку не подтверждай и не делай reboot
  вслепую. Сверь hook, штатный конфиг и подключённые файлы локально. Используй
  возврат только если скрипт подтверждает собственное состояние. При отказе
  нужен локальный способ восстановления.
- Новая установка требует отдельного пустого `--state-dir` и свободного порта,
  а на колонке — проверенного чистого состояния. Не переименовывай/не удаляй
  действующий каталог как способ скрыть проблему.

Полный stdout/stderr намеренно не выводится установщиком: в нём могут быть
секреты. Разбирай ошибку локально, не публикуй сырые ответы API и журналы.
`stack.json` и наличие файлов не заменяют проверку фактического состояния.

## 8. Возврат к штатной Алисе и остановка сервера

Сначала верни колонку, пока SSH и сервер доступны:

```sh
sudo python3 scripts/install.py rollback --target speaker --ssh alice-speaker
```

Подтверди `YES`. Команда ставит `disabled`, снимает только свой записанный
bind, останавливает свой мост/supervisor и сравнивает stock с оригиналом.
**Только после успеха** сделай контролируемый reboot:

```sh
sudo ssh alice-speaker reboot
```

Перезагрузка нужна из-за кеша endpoint в работающем голосовом процессе.
Проверь штатную Алису голосом. При отказе возврата не применяй `umount -f`,
массовый kill или запись поверх stock. Сохрани комплект и используй локальный
способ восстановления своей firmware. `rollback` не удаляет hook и резервные
файлы; это отключение, а не автоматическая очистка для переустановки.

Затем при необходимости останови **только созданный мастером** сервер:

```sh
sudo python3 scripts/install.py rollback --target server
```

Подтверди `YES`. Проверяется принадлежность stack; `docker compose down`
выполняется без удаления тома. Состояние и секреты остаются на сервере.
Не используй `down -v`, `docker volume prune` и общую остановку чужих проектов.

## 9. Закрытая резервная копия и восстановление сервера

Раздел относится к экземпляру, созданному `server/all`. Для существующего
чужого OmniRoute используй его собственный порядок резервирования.
Нужны **оба** архива: данные именованного тома и весь `/opt/alice-gemini`,
включая `gateway.env`, `station.json`, Compose/метаданные и оригинал колонки.
Без исходного encryption secret зашифрованные данные провайдера могут быть
недоступны. Архивы содержат ключи и данные устройства: root-only, вне Git,
при переносе — шифрование и доверенный канал.

Следующие команды на время останавливают **свой** работающий OmniRoute,
чтобы копия данных была согласованной. Выполняй в согласованное окно:

```sh
sudo sh <<'SH'
set -eu
umask 077
state=/opt/alice-gemini
backup=$(mktemp -d /root/alice-gemini-backup.XXXXXX)
container=$(docker compose --project-directory "$state" -f "$state/compose.json" ps --quiet omniroute)
test -n "$container"
docker compose --project-directory "$state" -f "$state/compose.json" stop omniroute >/dev/null
trap 'docker compose --project-directory "$state" -f "$state/compose.json" start omniroute >/dev/null' EXIT
docker cp "$container:/app/data/." - > "$backup/omniroute-data.tar"
tar -C /opt -cf "$backup/state.tar" alice-gemini
printf 'Закрытая копия: %s\n' "$backup"
SH
sudo python3 scripts/install.py check
```

`docker cp` здесь читает данные тома через остановленный контейнер; новый
вспомогательный образ не нужен. Не архивируй живую БД параллельно с записью.
Если копирование или повторный `check` не прошли, копия/работоспособность
не подтверждены. Не удаляй исходные данные.

Восстанавливай **на пустом сервере** с Python 3, Docker/Compose и тем же доступным LAN IP
либо с заранее согласованной новой сетевой настройкой. Не запускай `all`
поверх копии. Перенеси оба доверенных архива закрытым способом; замени путь
`backup` на фактический каталог копии. До выполнения блока проверь сохранённые
сетевые привязки в закрытой копии. Следующие команды отказывают при
существующем состоянии, контейнерах этого проекта или его томе:

```sh
sudo sh <<'SH'
set -eu
umask 077
state=/opt/alice-gemini
backup=/root/REPLACE_WITH_BACKUP_DIRECTORY
test -r "$backup/state.tar"
test -r "$backup/omniroute-data.tar"
test ! -e "$state"
test ! -L "$state"
tar -C /opt -xf "$backup/state.tar"
test "$(stat -c %u "$state")" = 0
test "$(stat -c %a "$state")" = 700
for name in gateway.env station.json compose.json stack.json; do
    test -f "$state/$name"
    test ! -L "$state/$name"
    test "$(stat -c %u "$state/$name")" = 0
    test "$(stat -c %a "$state/$name")" = 600
done
project=$(python3 -c 'import json; print(json.load(open("/opt/alice-gemini/stack.json"))["project"])')
test -z "$(docker ps -aq --filter "label=com.docker.compose.project=$project")"
if docker volume inspect "${project}_data" >/dev/null 2>&1; then
    printf '%s\n' 'Том уже существует; восстановление остановлено.' >&2
    exit 1
fi
docker compose --project-directory "$state" -f "$state/compose.json" create omniroute >/dev/null
container=$(docker compose --project-directory "$state" -f "$state/compose.json" ps --all --quiet omniroute)
test -n "$container"
docker cp -a - "$container:/app/data" < "$backup/omniroute-data.tar"
docker compose --project-directory "$state" -f "$state/compose.json" up -d --wait --wait-timeout 180 >/dev/null
SH
sudo python3 scripts/install.py check
```

Скрипт проверяет владельца root, каталог `0700` и файлы `0600` до старта
контейнера. Не показывай содержимое или хеши секретов.
После — вход администратора, `check`, доступ с колонки и голос. Эти команды
не являются заявлением о проведённом восстановлении на твоём оборудовании:
проверка восстановления на отдельном пустом сервере остаётся частью приёмки.
Не распаковывай незнакомые архивы с правами root.

## 10. Дом, офис и VPN

Смена Wi-Fi не создаёт маршрут к серверу. Нужен доступ **колонка → частный IP
OmniRoute** и **сервер → Google**, плюс доступ колонки к Яндексу. VPN только
на ноутбуке этого не обеспечивает. Если сеть недоверенная, обеспечь защищённый
маршрут на роутере/сети колонки либо отдельно настроенный HTTPS без отключения
проверки сертификата. Не открывай новый публичный порт и не делай factory
reset ради переноса. После смены сети повтори серверную проверку, проверку
backend с колонки, голос и проверяемый возврат.
